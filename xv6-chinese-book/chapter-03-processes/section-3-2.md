## 3.2 用户进程内存分配 (Memory Allocation for User Processes)

在上一节中，我们探讨了 xv6 中进程地址空间的整体布局。本节将聚焦于用户进程如何动态地获取和释放内存，特别是堆（Heap）的管理，以及相关的系统调用和内核机制。

### 1. 堆内存回顾 (Recap of the Heap)

回顾一下，堆是进程地址空间中位于 BSS 段之上、栈之下的一块区域。它的主要用途是**动态内存分配**，即允许程序在运行时根据需要请求任意大小的内存块，并在使用完毕后释放它们。与全局/静态变量（在编译时确定大小和位置）或局部变量（在栈上分配，随函数调用和返回自动管理）不同，堆内存的生命周期由程序员显式控制。

常见的动态内存分配场景包括：
*   创建大小在编译时未知的数据结构（例如，链表节点、树节点）。
*   读取用户输入或文件内容，其大小事先不确定。
*   实现可变长度的数组或字符串。

在 C 语言中，程序员通常通过标准库函数 `malloc()`、`calloc()`、`realloc()` 和 `free()` 来与堆内存交互。

### 2. `sbrk()` 系统调用：扩展与收缩堆

虽然用户程序使用 `malloc()` 和 `free()`，但这些库函数本身并不直接与物理内存打交道。当 `malloc()` 发现当前堆中没有足够的空间来满足分配请求时，它需要向操作系统内核请求更多的内存。在 xv6 (以及许多类 Unix 系统) 中，这是通过 `sbrk()` 系统调用完成的。

#### a. `sbrk()` 的用户视角

从用户程序的角度看，`sbrk(n)` 系统调用会调整进程数据段（包括 BSS 和堆）的上限。
*   如果 `n` 是正数，表示请求将堆的上限增加 `n` 字节。成功时，`sbrk()` 返回增加前的堆顶地址（即新分配内存区域的起始地址）。
*   如果 `n` 是负数，表示请求将堆的上限减少 `|n|` 字节（即释放内存回操作系统）。成功时，`sbrk()` 返回新的堆顶地址。
*   如果 `n` 是 0，`sbrk()` 返回当前的堆顶地址，而不做任何改变。
*   如果请求无法满足（例如，内存不足，或 `n` 的值导致堆顶与栈或其他区域冲突），`sbrk()` 返回 `(char*)-1`（一个表示错误的特殊值）。

用户程序通常不会直接调用 `sbrk()`，而是由 `malloc()` 这样的库函数在内部代为管理和调用。

#### b. xv6 中 `sbrk()` 的内核实现 (`sys_sbrk`)

当用户程序通过 `sbrk()` 系统调用请求改变其堆大小时，内核中的 `sys_sbrk()` 函数（位于 `kernel/sysproc.c`）会被执行。

```c
// kernel/sysproc.c
int
sys_sbrk(void)
{
  int addr;
  int n;
  struct proc *curproc = myproc(); // 获取当前进程的 proc 结构

  // 从用户栈获取 sbrk 的参数 n
  if(argint(0, &n) < 0) // argint(0, &n) 从用户栈获取第0个参数（即n）
    return -1;

  addr = curproc->sz; // curproc->sz 存储了当前进程的总大小（堆的当前上限）
  if(growproc(n) < 0) // 调用 growproc 尝试调整进程大小
    return -1;
  return addr; // 成功则返回旧的堆顶地址 (即新分配区域的起始地址)
}
```

`sys_sbrk()` 的逻辑很简单：
1.  获取当前进程的 `struct proc` 指针。
2.  使用 `argint()` 从用户栈中提取传递给 `sbrk()` 的参数 `n`（要增加或减少的字节数）。
3.  记录当前进程的大小 `curproc->sz` 到 `addr` 变量。这个 `sz` 代表了进程当前已分配内存的上限（不包括栈）。
4.  调用 `growproc(n)` 函数，尝试将进程的大小调整 `n` 字节。
5.  如果 `growproc(n)` 成功（返回 0 或更大值），则 `sys_sbrk()` 返回原始的 `addr`（即旧的堆顶，新分配内存的起始点）。
6.  如果 `growproc(n)` 失败（返回 -1），则 `sys_sbrk()` 也返回 -1。

#### c. `growproc()`：实际调整进程内存

`growproc(n)` 函数（位于 `kernel/proc.c`）负责实际增加或减少进程的内存占用。

```c
// kernel/proc.c
int
growproc(int n)
{
  uint sz;
  struct proc *curproc = myproc();

  sz = curproc->sz;
  if(n > 0){ // 如果 n > 0，表示要增加内存 (扩展堆)
    // 调用 allocuvm 分配新的虚拟内存页，并建立页表映射
    if((sz = allocuvm(curproc->pgdir, sz, sz + n)) == 0)
      return -1; // 分配失败
  } else if(n < 0){ // 如果 n < 0，表示要减少内存 (收缩堆)
    // 调用 deallocuvm 释放虚拟内存页，并清除页表映射
    if((sz = deallocuvm(curproc->pgdir, sz, sz + n)) == 0)
      return -1; // 释放失败
  }
  curproc->sz = sz; // 更新进程的内存大小
  switchuvm(curproc); // 切换到当前进程的页表 (确保 TLB 等刷新)
  return 0;
}
```
`growproc()` 的逻辑如下：

*   获取当前进程的大小 `curproc->sz`。
*   **扩展堆 (n > 0)**：
    *   调用 `allocuvm(curproc->pgdir, oldsz, newsz)` 函数。`allocuvm`（在 `kernel/vm.c` 中）负责在指定的页目录 `curproc->pgdir` 下，为从旧大小 `oldsz` 到新大小 `newsz` (`oldsz + n`) 的虚拟地址范围分配物理内存页，并建立相应的页表映射。
    *   `allocuvm` 会逐页进行分配。对于每一页，它会调用 `kalloc()`（见后文）获取一个空闲的物理页帧，然后用 `mappages()` 将该物理页帧映射到用户进程的虚拟地址空间中。
    *   如果 `allocuvm` 成功，它返回新的进程大小 `newsz`。如果中途失败（例如 `kalloc()` 无法分配到物理页），它会返回 0。
*   **收缩堆 (n < 0)**：
    *   调用 `deallocuvm(curproc->pgdir, oldsz, newsz)` 函数。`deallocuvm`（也在 `kernel/vm.c` 中）负责释放从新大小 `newsz` (`oldsz + n`) 到旧大小 `oldsz` 的虚拟地址范围所占用的物理内存页，并清除相应的页表项。
    *   `deallocuvm` 会逐页进行操作。对于每一页，它首先会清除页表项，然后调用 `kfree()`（见后文）将对应的物理页帧归还给内核的空闲物理页池。
    *   如果 `deallocuvm` 成功，它返回新的进程大小 `newsz`。如果失败（例如，尝试释放一个无效的地址范围），它会返回 0。
*   更新进程大小：如果 `allocuvm` 或 `deallocuvm` 成功，将 `curproc->sz` 更新为新的大小 `sz`。
*   `switchuvm(curproc)`：这个函数用于确保 CPU 使用的是当前进程的页表。在多处理器系统中，它还可能需要处理 TLB (Translation Lookaside Buffer) 的刷新，以确保地址翻译使用最新的页表信息。
*   返回 0 表示成功，-1 表示失败。

**`allocuvm` 和 `deallocuvm` 的关键点：**
*   这两个函数操作的是用户虚拟内存（User Virtual Memory）。
*   它们以页（大小为 `PGSIZE`，在 xv6 中是 4096 字节）为单位进行分配和释放。
*   它们不仅分配/释放物理内存，还负责建立/清除页目录和页表中的映射关系（PDEs 和 PTEs）。
*   它们会检查请求的地址范围是否超出了用户空间允许的最大范围（`KERNBASE`）。

### 3. 用户空间的 `malloc()` 和 `free()`

虽然内核通过 `sbrk()` 提供了扩展堆的机制，但直接使用 `sbrk()` 来管理小块内存效率低下（每次分配小块内存都可能涉及系统调用和页分配）且不方便（需要自己跟踪大小和地址）。因此，用户程序通常依赖于用户态的内存分配库，如 C 标准库中的 `malloc()` 和 `free()`。

xv6 提供了一个非常简单的 `malloc()` 和 `free()` 实现，位于 `user/umalloc.c`。

#### a. `malloc()` 的基本原理

`malloc(nbytes)` 的目标是从堆中找到一块大小至少为 `nbytes` 的连续空闲内存返回给调用者。
1.  **维护空闲链表 (Free List)**：`user/umalloc.c` 中的 `malloc` 实现使用了一个简单的空闲块链表。每个空闲块都有一个头部（`Header` 结构），记录了该块的大小和指向下一个空闲块的指针。
2.  **查找合适的空闲块**：当 `malloc` 被调用时，它会遍历这个空闲链表，寻找第一个大小足够容纳请求字节数（加上头部大小）的空闲块（首次适应 First Fit 策略）。
3.  **分割空闲块**：如果找到的空闲块比请求的大小要大得多，`malloc` 可能会将其分割成两部分：一部分满足请求并返回给用户，另一部分变小后仍然保留在空闲链表中。
4.  **请求更多内存 (`sbrk`)**：如果遍历完空闲链表都没有找到足够大的块，`malloc` 就会调用 `sbrk()` 向内核请求更多的内存。`sbrk()` 返回的新内存区域会被 `malloc` 视为一个大的空闲块，并加入到空闲链表中，然后再次尝试从中分配。`user/umalloc.c` 中的 `morecore()` 函数封装了对 `sbrk()` 的调用。
5.  **返回指针**：一旦分配成功，`malloc` 返回指向实际可用内存区域（即头部之后）的指针。

#### b. `free()` 的基本原理

`free(ptr)` 的目标是将 `ptr` 指向的之前由 `malloc` 分配的内存块归还给空闲链表，以便后续的 `malloc` 调用可以重用它。
1.  **获取块头部**：`free` 首先通过 `ptr` 向前偏移找到对应的块头部。
2.  **添加到空闲链表**：然后，它将这个块插入到空闲链表的适当位置（`user/umalloc.c` 的实现是将其插入到链表头部）。
3.  **合并空闲块 (Coalescing)**：理想情况下，`free` 还会检查被释放块相邻的块是否也是空闲的。如果是，则将它们合并成一个更大的空闲块，以减少内存碎片。xv6 的 `user/umalloc.c` 实现了一个简单的合并逻辑，它会尝试与前一个被释放的块（如果它们在内存中是连续的）以及链表中物理地址上紧随其后的块进行合并。

#### c. `malloc` 与 `sbrk` 的关系

*   `malloc` 是用户态库函数，`sbrk` 是系统调用。
*   `malloc` 管理用户进程堆中的小块内存分配和释放。
*   当 `malloc` 需要更多堆空间来满足分配请求时，它会调用 `sbrk` 向内核“批发”一大块内存。
*   `free` 通常不会立即将内存归还给操作系统（即调用 `sbrk` 传入负值），而是将内存块标记为空闲并保留在用户态的空闲链表中，以备后续 `malloc` 使用。只有在特定情况下，一些高级的 `malloc` 实现可能会尝试收缩堆。xv6 的 `user/umalloc.c` 中的 `free` 不会主动调用 `sbrk` 来收缩堆。

### 4. 内核的物理内存管理 (`kalloc()` 和 `kfree()`)

用户进程通过 `sbrk()` -> `growproc()` -> `allocuvm()` 最终获得的内存，其物理来源是内核管理的空闲物理页池。内核本身也需要动态分配内存（例如，为页表、内核栈、管道缓冲区等分配空间）。

xv6 在 `kernel/kalloc.c` 中实现了一个简单的物理页帧分配器：

*   **空闲链表 (`kmem.freelist`)**: 内核维护一个空闲物理页的链表。每个节点是一个 `struct run`，它简单地包含一个指向下一个空闲页的指针。这个链表是在系统启动时，通过 `freerange()` 函数将 `end`（内核代码和数据结束之后）到 `PHYSTOP`（可用物理内存的顶端）之间的所有物理内存逐页加入的。
*   **`kalloc()`**: 当需要分配一个物理页时（例如，`allocuvm` 为用户分配新页，或内核自身需要页），`kalloc()` 函数会：
    1.  获取 `kmem.lock` 自旋锁。
    2.  从 `kmem.freelist` 链表头取下一个空闲页（`struct run *r = kmem.freelist;`）。
    3.  如果链表不为空，则更新链表头 (`kmem.freelist = r->next;`)。
    4.  释放锁。
    5.  如果成功获取到页，`kalloc()` 可能会用一个特殊值（如 1）填充该页，以帮助暴露那些错误地使用了未初始化内存的 bug。
    6.  返回该物理页的虚拟地址（内核将整个物理内存直接映射到了内核地址空间）。如果 `kmem.freelist` 为空，则返回 0 (null)，表示分配失败。
*   **`kfree(v)`**: 当一个物理页不再需要时（例如，`deallocuvm` 释放用户页，或内核释放其自身使用的页），`kfree()` 函数会：
    1.  检查地址 `v` 是否合法（例如，是否页对齐，是否在允许的范围内）。
    2.  获取 `kmem.lock`。
    3.  将地址 `v` 强制转换为 `struct run*`，并将其插入到 `kmem.freelist` 的头部。
    4.  释放锁。

所以，整个流程是：用户 `malloc` -> (可能调用) 用户 `sbrk` -> 内核 `sys_sbrk` -> 内核 `growproc` -> 内核 `allocuvm` -> 内核 `kalloc` -> 从内核空闲物理页池获取页。

### 5. xv6 内存分配的局限性

xv6 的内存管理和分配机制为了教学目的而设计得相对简单，它存在一些局限性，与现代商业操作系统相比：

*   **没有真正的按需分页 (Demand Paging)**：当 `exec` 加载程序时，它会一次性为代码段和数据段分配并加载所有需要的物理内存。栈也是在第一次页错误时分配一整页，但不是更细粒度的按需调页。现代系统通常使用按需分页，即只在页被实际访问时才加载它，从而加快程序启动速度并节省内存。
*   **简单的 `sbrk` 模型**：`sbrk` 只能线性地增长或收缩进程数据段的末尾。它不能在进程地址空间中间创建或释放内存区域。这使得像 `mmap` 和 `munmap` 这样的更灵活的内存管理接口无法实现。
*   **无内存交换 (Swapping)**：如果物理内存耗尽，xv6 的 `kalloc` 会失败，进而可能导致 `sbrk` 或其他内核分配失败。它不会像一些操作系统那样，将不活动的内存页临时换出到磁盘（交换空间）来腾出物理内存。
*   **用户态 `malloc` 简单**：`user/umalloc.c` 中的 `malloc` 和 `free` 实现非常基础，其碎片管理和性能可能不如成熟的分配器（如 dlmalloc, jemalloc, tcmalloc）。它主要用于演示基本原理。
*   **内核内存碎片**：`kalloc` 和 `kfree` 是基于页的分配器。内核自身如果需要小于一页的内存，也必须分配整页，可能会导致内部碎片。不过 xv6 内核相对较小，动态分配需求不多。

尽管存在这些局限性，xv6 的内存分配机制清晰地展示了操作系统管理用户进程堆内存所需的核心步骤，包括系统调用接口、内核对进程大小的跟踪、以及虚拟内存与物理内存的分配和映射。这是理解更复杂内存管理系统的良好起点。
