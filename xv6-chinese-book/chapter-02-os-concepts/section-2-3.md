## 2.3 进程详解 (Processes in Detail)

进程是操作系统中一个至关重要的概念，它是程序执行的动态实例。本节将深入探讨 xv6 是如何表示、创建、管理和调度进程的。

### 1. 进程回顾 (Recap of Processes)

正如我们在 2.1 节中提到的，一个进程并不仅仅是一段可执行的代码。它是一个正在运行的程序的完整体现，拥有自己独立的：

*   **内存空间 (Address Space)**：包括程序的代码、全局变量、栈（用于函数调用和局部变量）和堆（用于动态内存分配）。
*   **CPU 状态 (CPU State)**：主要由寄存器的值表示，如程序计数器（PC，指向下一条要执行的指令）、栈指针（ESP）、通用寄存器等。
*   **内核资源 (Kernel Resources)**：如打开的文件描述符列表、当前工作目录等。
*   **执行状态 (Execution State)**：表明进程当前的活动，例如正在运行、等待 I/O 或已准备好运行。

操作系统负责在多个进程之间共享 CPU 和其他硬件资源，并确保它们能够并发、安全地执行。

### 2. xv6 中的进程表示 (Process Representation in xv6)

xv6 内核需要一种方式来跟踪和管理系统中的所有进程。这是通过进程表（process table）和每个进程对应的进程控制块（Process Control Block, PCB）来实现的。

#### a. `struct proc`：进程控制块

在 xv6 中，每个进程都由一个 `struct proc` 结构体（定义在 `kernel/proc.h` 中）来表示。这个结构体包含了内核管理一个进程所需的所有信息。以下是一些关键字段的解释：

*   **`uint sz`**: 进程的内存大小（以字节为单位）。
*   **`pde_t* pgdir`**: 指向该进程的页目录（Page Directory）的指针。页目录是实现每个进程独立地址空间的关键，用于虚拟地址到物理地址的转换。
*   **`char *kstack`**: 指向该进程的内核栈顶部的指针。当进程从用户态切换到内核态（例如，在系统调用或中断期间），它会使用这个内核栈。内核栈独立于用户栈，并且位于内核的地址空间中，对用户程序不可见。
*   **`enum procstate state`**: 表示进程的当前状态。xv6 定义了以下几种状态：
    *   **`UNUSED`**: 表示此 `struct proc` 结构体槽位当前未被使用，可供新进程分配。
    *   **`EMBRYO`**: 进程正在被创建，但尚未准备好运行。这是 `fork()` 系统调用过程中的一个中间状态。
    *   **`SLEEPING`**: 进程正在等待某个事件的发生，因此暂时被阻塞。例如，等待磁盘 I/O 完成（如 `read()` 文件）、等待子进程退出（如 `wait()`）或等待 `sleep()` 系统调用超时。处于 `SLEEPING` 状态的进程不会被调度器选中运行。
    *   **`RUNNABLE`**: 进程已准备好运行，拥有所有必要的资源，只等待 CPU 分配时间片。调度器会从处于 `RUNNABLE` 状态的进程中选择一个来运行。
    *   **`RUNNING`**: 进程当前正在某个 CPU 上执行其用户态或内核态代码。
    *   **`ZOMBIE`**: 进程已经完成了它的执行（通常是通过调用 `exit()` 系统调用），但它的父进程尚未通过 `wait()` 系统调用来获取其退出状态并清理其资源。此时，进程的大部分资源（如内存、打开的文件）已被释放，但 `struct proc` 结构体本身仍然保留，以便父进程可以查询其退出状态。

*   **`int pid`**: 进程 ID（Process ID），一个唯一的整数，用于标识该进程。
*   **`struct proc *parent`**: 指向该进程的父进程的指针。除了第一个进程外，所有进程都是由其他进程创建的。
*   **`struct trapframe *tf`**: 指向该进程的陷阱帧（Trap Frame）的指针。当进程从用户态切换到内核态时（通过系统调用或中断），CPU 的寄存器状态（如 `%eax`, `%ebx`, `%eip`, `%esp` 等）会被保存在这个陷阱帧中。当从内核态返回用户态时，这些寄存器会被恢复，使得用户程序可以从中断的地方继续执行。
*   **`struct context *context`**: 指向该进程的上下文（Context）的指针。上下文存储了进程在内核态执行时，进行进程切换（context switch）所需要保存的最小寄存集。这主要包括一些被调用者保存的寄存器（callee-saved registers）以及内核栈指针 (`%esp`) 和指令指针 (`%eip`)。当调度器决定切换到另一个进程时，当前进程的上下文被保存；当调度器决定恢复这个进程时，它的上下文被恢复。`swtch()` 函数负责这个保存和恢复的过程。
*   **`void *chan`**: 如果进程处于 `SLEEPING` 状态，`chan` 通常指向一个表示等待事件的任意内核数据结构地址（例如，等待某个特定的磁盘缓冲区）。当事件发生时，内核会通过这个 `chan` 值来唤醒所有等待在该“通道”上的进程。如果进程不处于 `SLEEPING` 状态，`chan` 通常为 0。
*   **`int killed`**: 一个标志位。如果设置为 1，表示该进程已被标记为“杀死”（通常通过 `kill()` 系统调用）。进程在下一次从内核态返回用户态之前，或者在某些可中断的睡眠点，会检查这个标志并自行退出。
*   **`struct file *ofile[NOFILE]`**: 一个数组，存储了该进程打开的文件描述符所对应的文件结构指针。`NOFILE` 是每个进程能打开的最大文件数。
*   **`struct inode *cwd`**: 指向该进程当前工作目录（Current Working Directory）的 inode 结构的指针。

#### b. 进程表 (`ptable`)

xv6 内核维护一个全局的进程表，它是一个 `struct proc` 类型的数组。
```c
struct proc proc[NPROC]; // NPROC 是系统允许的最大进程数，在 param.h 中定义
```
这个进程表通常被一个自旋锁 `ptable.lock` 保护，以确保在多处理器环境下对进程表的操作是原子的。当内核需要分配一个新的进程结构、查找一个特定 `pid` 的进程或遍历所有进程时，都会访问这个表。

### 3. xv6 中的进程生命周期 (Process Lifecycle in xv6)

一个进程从创建到最终消亡，会经历几个关键阶段。

#### a. 进程创建 (`fork()`)

`fork()` 是 xv6 (以及所有类 Unix 系统) 中创建新进程的主要方式。调用 `fork()` 的进程称为父进程，新创建的进程称为子进程。`fork()` 的一个奇特之处在于它在父进程中被调用一次，但返回两次：在父进程中返回子进程的 `pid`，在子进程中返回 0。

`fork()` 的实现（主要在 `kernel/proc.c` 中的 `fork()` 函数）大致执行以下步骤：

1.  **分配进程结构 (`allocproc()`)**:
    *   内核首先调用 `allocproc()` 来从进程表 `ptable` 中寻找一个状态为 `UNUSED` 的 `struct proc` 槽位。
    *   如果找到，将其状态设置为 `EMBRYO`，并为其分配一个唯一的 `pid`。
    *   关键的一步是为子进程分配内核栈 (`kstack`)。如果分配失败，则将该 `struct proc` 状态重置为 `UNUSED` 并返回失败。
    *   在内核栈的底部，`allocproc()` 会精心设置一些值，使得当这个新进程第一次被调度执行时，它看起来像是从一个特定的函数返回。具体来说，它会设置一个返回地址指向 `forkret`，再往上是 `trapret`。同时，`context` 结构中的 `%eip` (指令指针) 会被设置为指向 `forkret` 函数。

2.  **复制父进程内存 (`copyuvm()`)**:
    *   子进程的初始内存映像是父进程内存的精确副本。`fork()` 调用 `copyuvm()` (在 `kernel/vm.c` 中) 来为子进程创建一个新的页目录，并将父进程的用户空间内存逐页复制到子进程的物理内存中。这包括代码段、数据段和用户栈。如果内存复制失败（例如，物理内存不足），`fork()` 会清理已分配的资源并返回失败。

3.  **复制父进程状态**:
    *   子进程继承父进程大部分其他的状态，例如：
        *   **文件描述符**: 通过 `filedup()` 复制父进程的打开文件表 `ofile`。这意味着子进程和父进程共享相同的文件偏移量。
        *   **当前工作目录**: 复制父进程的 `cwd` 指针。
    *   子进程的陷阱帧 (`tf`) 是父进程陷阱帧的一个副本。这对子进程从 `fork()` 返回后的执行至关重要。父进程的 `%eax` 寄存器在陷阱帧中被设置为子进程的 `pid`（这是父进程 `fork` 的返回值）。而对于子进程，其陷阱帧中的 `%eax` 被显式设置为 0（这是子进程 `fork` 的返回值）。

4.  **设置子进程为可运行**:
    *   完成所有复制和设置后，子进程的 `sz` (内存大小) 被设置为与父进程相同。
    *   父进程的 `pid` 被记录在子进程的 `parent` 字段。
    *   子进程的 `state` 从 `EMBRYO` 更改为 `RUNNABLE`，这意味着它现在可以被调度器选中并在 CPU 上运行了。

5.  **返回**: `fork()` 在父进程中返回子进程的 `pid`。子进程在未来某个时刻被调度执行时，它会从 `forkret` 开始，然后通过 `trapret` 返回到用户空间，此时其 `%eax` 寄存器的值为 0，就像 `fork()` 在子进程中返回了 0 一样。

#### b. 进程运行与调度 (Running and Scheduling)

一旦一个进程的状态变为 `RUNNABLE`，它就有资格被 CPU 执行。xv6 的调度器（在 `scheduler()` 函数中，位于 `kernel/proc.c`）负责选择下一个要运行的进程。

*   **调度器 (`scheduler()`)**: 每个 CPU 核心都会运行一个 `scheduler()` 函数。它会循环遍历进程表 `ptable`，寻找状态为 `RUNNABLE` 的进程。
*   **上下文切换 (`swtch()`)**: 当调度器找到一个 `RUNNABLE` 的进程后，它会执行上下文切换，将 CPU 从当前的调度器上下文切换到选中的用户进程的内核上下文。
    *   在切换之前，当前 CPU 的 `cpu->scheduler`（指向调度器自身的上下文）和目标进程的 `proc->context` 会被传递给 `swtch()` 函数（在 `kernel/swtch.S` 中）。
    *   `swtch()` 是一个汇编函数，它负责：
        1.  保存当前上下文（调度器或上一个用户进程的内核上下文）的寄存器（如 `%ebp`, `%esp`, `%ebx`, `%esi`, `%edi`, `%eip`）到当前上下文结构中。
        2.  加载新进程上下文结构中保存的寄存器值到 CPU 的实际寄存器中。
    *   当 `swtch()` 返回时，CPU 的指令指针 `%eip` 已经指向了新进程的上下文之前保存的 `%eip`，栈指针 `%esp` 也指向了新进程的内核栈。如果这个新进程是第一次被调度（即刚从 `fork()` 创建），它的 `%eip` 会指向 `forkret`。如果它是之前运行过被切换出去的，它的 `%eip` 会指向它在 `swtch()` 调用中被中断的地方。
*   **`forkret()`**: 对于一个新创建的子进程，它首次被调度时会执行 `forkret()`。`forkret()` 主要做一些解锁操作（释放 `ptable.lock`，这个锁是在 `allocproc` 或 `scheduler` 中获取的）。然后，它会调用 `trapret`。
*   **`trapret()`**: 这个汇编函数（在 `kernel/vectors.S` 中）负责从内核态安全地返回到用户态。它从当前进程的陷阱帧 (`tf`) 中恢复所有用户态寄存器（包括用户态的 `%eip` 和 `%esp`），然后执行 `iret` 指令，使 CPU 切换回用户态并从用户态的 `%eip` 开始执行。对于子进程来说，它将从 `fork()` 系统调用之后的地方开始执行，并得到返回值 0。

一个进程会持续运行，直到：
*   它自愿放弃 CPU（例如，调用 `sleep()` 或 `wait()` 进入 `SLEEPING` 状态）。
*   它执行完毕并调用 `exit()`。
*   发生时钟中断，内核可能会决定抢占该进程，将其状态改回 `RUNNABLE`，并调度另一个进程（xv6 的调度是协作式的，主要在系统调用或中断返回时发生调度机会，但时钟中断是实现抢占的基础）。
*   发生其他中断或异常，导致其执行被暂停。

#### c. 进程终止 (`exit()`)

当一个进程完成其任务后，它会调用 `exit()` 系统调用来终止自己。`exit()` 函数（在 `kernel/proc.c` 中）执行以下操作：

1.  **关闭打开的文件**: 遍历进程的 `ofile` 数组，对每个打开的文件调用 `fileclose()`。
2.  **释放当前工作目录**: 调用 `iput()` 释放对当前工作目录 inode 的引用。
3.  **唤醒父进程**: 如果父进程正在 `wait()` 调用中等待该子进程退出，则唤醒父进程。
4.  **处理子进程**: 将当前进程的所有子进程的 `parent` 指针重新指向系统的第一个用户进程 `initproc`。这是为了确保孤儿进程（父进程先于子进程退出的子进程）仍然有一个父进程来最终回收它们。
5.  **改变状态为 `ZOMBIE`**: 将当前进程的 `state` 设置为 `ZOMBIE`。此时，进程的大部分资源（如用户内存、页表）尚未释放，它们将在父进程调用 `wait()` 时被清理。进程变为 `ZOMBIE` 状态后，它不再会被调度执行。
6.  **调用调度器**: 调用 `sched()` 函数，该函数内部会调用 `swtch()` 来放弃 CPU，让调度器选择另一个进程运行。进程永远不会从对 `sched()` 的调用中返回，因为它已经不再是 `RUNNABLE` 状态了。

#### d. 等待子进程 (`wait()`)

父进程通常需要等待其创建的子进程结束，并获取其退出状态。这是通过 `wait()` 系统调用完成的。`wait()` 函数（在 `kernel/proc.c` 中）执行以下操作：

1.  **扫描子进程**: 循环遍历进程表 `ptable`，查找调用者（当前进程）的子进程。
2.  **寻找僵尸子进程**: 如果找到了一个状态为 `ZOMBIE` 的子进程：
    *   获取该僵尸子进程的 `pid`（作为 `wait()` 的返回值）。
    *   **清理资源**: 释放僵尸子进程的内核栈 (`kfree(p->kstack)`)，释放其页目录和用户内存 (`freevm(p->pgdir)`)。
    *   将僵尸子进程的 `struct proc` 槽位状态设置为 `UNUSED`，并清空其 `pid`, `parent` 指针等字段，使其可以被后续的 `allocproc()` 重用。
    *   返回子进程的 `pid`。
3.  **如果没有僵尸子进程**:
    *   如果调用者有子进程，但它们都还在运行（不是 `ZOMBIE` 状态），则父进程会调用 `sleep(proc, &ptable.lock)` 使自己进入 `SLEEPING` 状态，等待其任何一个子进程退出。当有子进程调用 `exit()` 时，它会唤醒其父进程。
    *   如果调用者没有任何子进程（或者之前所有的子进程都已经被 `wait` 回收了），`wait()` 会立即返回 -1，表示没有子进程可等待。
4.  **处理 `killed` 标志**: 如果父进程在 `sleep` 期间被 `kill` 了，`wait` 会返回 -1。

**僵尸进程 (Zombie Processes)**：如果一个进程已经 `exit()` 变成了 `ZOMBIE`，但其父进程没有（或尚未）调用 `wait()` 来回收它，那么这个 `ZOMBIE` 进程的 `struct proc` 结构就会一直保留在进程表中。虽然它不占用太多资源（大部分内存已释放），但它仍然占据进程表中的一个槽位。如果大量产生这样的僵尸进程而没有被回收，最终可能导致进程表被占满，使得系统无法创建新进程。`initproc` 的一个重要职责就是循环调用 `wait()` 来回收所有成为孤儿的僵尸进程。

### 4. 第一个进程 (`initproc` 与 `userinit`)

当 xv6 内核启动完成后，它需要创建第一个用户进程。这个特殊的进程称为 `initproc`。

*   **`userinit()`**: 内核在 `main()` 函数（`kernel/main.c`）的最后阶段会调用 `userinit()`（`kernel/proc.c`）。
*   `userinit()` 的作用是：
    1.  调用 `allocproc()` 分配一个 `struct proc` 结构给 `initproc`。
    2.  为 `initproc` 设置好页目录 (`setupkvm()`)，并初始化一小段用户空间内存，这段内存包含了 `initcode.S`（`kernel/initcode.S`）的二进制代码。`initcode.S` 是一段非常小的汇编程序，它的功能是执行 `exec("/init", argv)` 系统调用。
    3.  设置 `initproc` 的陷阱帧，使其看起来像是从内核态返回到用户态，并从 `initcode.S` 的起始地址开始执行。`%esp` 指向 `initcode.S` 的栈。
    4.  将 `initproc` 的 `sz`（大小）设置为 `initcode.S` 占用的内存页大小。
    5.  将 `initproc` 的 `state` 设置为 `RUNNABLE`。
    6.  `initproc` 的 `cwd`（当前工作目录）被设置为根目录。

*   **`/init` 程序**: `initcode.S` 执行 `exec("/init", ...)` 后，内核会加载 `/init` 用户程序（源码在 `user/init.c`）。`/init` 程序通常执行以下任务：
    1.  如果需要，创建控制台设备文件 (`mknod`)。
    2.  打开标准输入、输出、错误文件描述符（0, 1, 2）。
    3.  循环执行：
        *   启动一个 shell (`fork()` 然后 `exec("sh", ...)`）。
        *   调用 `wait()` 等待子进程（如 shell 或其他孤儿进程）退出。如果一个子进程退出了，`init` 会打印一些信息并继续循环。
    `init` 进程永远不会退出。它是所有孤儿进程的最终父进程，负责清理它们。

### 5. 上下文切换 (`swtch()`)

上下文切换是操作系统实现多任务的核心机制。它指的是 CPU 从一个正在执行的进程（或内核线程，如调度器）切换到另一个进程的过程。这个过程涉及到保存当前执行环境的状态，并恢复新进程的执行环境。

在 xv6 中，上下文切换由 `swtch()` 函数（`kernel/swtch.S`）执行。
*   `swtch(struct context **old, struct context *new)` 接受两个参数：一个指向旧上下文结构体指针的指针 (`old`)，以及一个指向新上下文结构体的指针 (`new`)。
*   **保存旧上下文**: `swtch()` 首先将当前 CPU 的一些关键寄存器（`%ebp`, `%ebx`, `%esi`, `%edi`, `%esp`, `%eip` - 指令指针是通过 `call swtch` 间接保存的，而 `%esp` 是直接保存的）压入 `*old` 指向的上下文结构中。
*   **加载新上下文**: 然后，它从 `new` 指向的上下文结构中，将之前保存的寄存器值加载回 CPU 的相应寄存器。
*   **返回**: 当 `swtch()` 从 `new` 上下文中恢复了 `%eip`（指令指针）并执行 `ret` 指令时，CPU 就开始执行新上下文所指向的代码了。

`swtch()` 只保存和恢复那些在 C 函数调用之间需要由被调用者保存的寄存器（callee-saved registers），以及栈指针和指令指针。它不保存通用寄存器如 `%eax`, `%ecx`, `%edx`（caller-saved registers），也不保存段寄存器或浮点寄存器（xv6 内核不使用浮点运算）。这是因为 `swtch()` 总是在内核态、C 函数的上下文中被调用（例如，`scheduler()` 调用 `swtch()` 切换到用户进程的内核上下文，或者 `sched()` 函数在进程放弃 CPU 时调用 `swtch()` 切换回调度器上下文）。调用 `swtch()` 的 C 代码负责在需要时保存调用者保存的寄存器。

理解进程的表示、生命周期和上下文切换机制是掌握 xv6 内核运作方式的关键一步。这些机制共同构成了 xv6 多任务处理的基础。
