# 第 5 章：文件系统

在前面的章节中，我们探讨了进程和内存管理。然而，这些信息在计算机关机后就会丢失。为了持久化地存储数据，操作系统需要提供文件系统。本章将深入 xv6 文件系统的设计与实现。

## 5.1 文件系统概览 (File System Overview)

### 1. 文件系统简介 (Introduction to File Systems)

**什么是文件系统？**

文件系统是操作系统中用于管理持久性存储（通常是硬盘、SSD等）上数据的部分。它负责组织、存储、检索和管理用户数据和程序。如果没有文件系统，存储设备上的数据将只是一片无序的字节海洋，难以使用。

**为什么需要文件系统？**

文件系统提供了几个关键功能：

*   **持久性存储 (Persistent Storage)**：最基本的功能。文件系统使得数据在计算机关闭或程序结束后仍然存在。
*   **命名 (Naming)**：用户可以通过有意义的名称（文件名）来识别和访问数据，而不是通过物理块号。
*   **组织 (Organization)**：文件系统通常提供层次化的目录结构（文件夹），允许用户将文件组织成逻辑分组，方便管理和查找。
*   **访问控制 (Access Control)**：虽然 xv6 的模型简单，但多数文件系统提供机制来控制不同用户对文件的访问权限（读、写、执行）。
*   **共享 (Sharing)**：允许多个进程或用户共享文件数据。
*   **抽象 (Abstraction)**：文件系统向用户和应用程序提供了一个统一的、抽象的接口来访问不同类型的存储设备，隐藏了底层硬件的复杂细节。例如，无论是向硬盘写入还是向U盘写入（xv6中不直接支持U盘，但原理类似），应用程序都可能使用相同的 `write()` 系统调用。

### 2. xv6 文件系统架构 (xv6 File System Architecture)

xv6 实现了一个简单但完整的类 Unix 文件系统。它的设计采用了分层的方法，每一层为其上一层提供服务，并使用其下一层的服务。这种分层结构有助于模块化和简化设计。从上到下，主要的层次包括：

1.  **用户接口层 (User Interface Layer)**：
    *   这是最顶层，应用程序通过系统调用（如 `open`, `read`, `write`, `close`, `link`, `unlink`, `mkdir`, `chdir` 等）与文件系统交互。
    *   这一层将用户提供的路径名和文件描述符转换为更底层的操作。

2.  **路径名遍历/查找层 (Pathname Traversal/Lookup Layer)**：
    *   当系统调用涉及路径名（如 `open("/usr/xv6/cat")`）时，这一层负责解析路径。
    *   它会从根目录或当前目录开始，逐级查找路径中的每个组成部分，最终定位到目标文件或目录的 inode（索引节点）。
    *   相关函数如 `namei()`, `nameiparent()`。

3.  **Inode 操作层 (Inode Operations Layer)**：
    *   一旦找到了目标 inode，文件系统的操作就围绕 inode 进行。
    *   这一层负责 inode 的分配、释放、读取和修改。它处理文件的元数据（如类型、大小、块地址等）。
    *   它还实现了对 inode 锁的获取和释放，以保证并发操作的正确性。
    *   相关函数如 `ialloc()`, `iget()`, `iput()`, `readi()`, `writei()`。

4.  **文件内容与目录逻辑层 (File Content and Directory Logic Layer)**：
    *   对于普通文件，这一层通过 inode 中的块地址信息，将文件内的逻辑偏移量（例如，读取文件的第500个字节）转换为磁盘上的物理块号，然后进行读写。函数如 `bmap()` 负责这个映射。
    *   对于目录，这一层负责解析目录内容（即 `struct dirent` 条目列表），实现查找目录项、添加目录项、删除目录项等操作。

5.  **缓冲区缓存层 (Buffer Cache Layer)**：
    *   为了提高性能并减少对磁盘的直接访问次数，xv6 实现了一个磁盘块的缓冲区缓存（`bio.c`）。
    *   当需要读取磁盘块时，首先在缓存中查找。如果命中，则直接从内存返回数据；如果未命中，则从磁盘读取该块到缓存中，然后再返回。
    *   对磁盘的写操作也可能先写入缓存（延迟写），然后由缓存层在合适的时机写回磁盘。
    *   相关函数如 `bread()`, `bwrite()`, `brelse()`。

6.  **日志层 (Logging Layer)**：
    *   为了保证文件系统在发生崩溃（如突然断电）后的一致性，xv6 实现了一个简单的日志系统（`log.c`）。
    *   文件系统操作（如创建一个文件）可能涉及对磁盘多个块的修改（例如，inode块、数据块、位图块）。如果在修改过程中发生崩溃，可能导致文件系统状态不一致。
    *   日志系统通过“预写日志”（Write-Ahead Logging）的原则工作：在实际修改磁盘上的文件系统结构之前，先将描述这些修改的日志条目写入磁盘上的一个专用日志区域。如果在修改过程中崩溃，系统重启后可以通过重放日志来恢复一致性。
    *   所有对磁盘块的修改都必须通过日志层进行包装。

7.  **磁盘驱动层 (Disk Driver Layer)**：
    *   这是最底层，负责与实际的磁盘硬件（在QEMU中是模拟的IDE硬盘）进行通信。
    *   它将对逻辑块号的读写请求转换为对磁盘扇区的具体硬件操作（例如，通过I/O端口发送命令给磁盘控制器）。
    *   相关函数如 `iderw()`。

### 3. xv6 磁盘上的文件系统布局 (On-Disk Structures in xv6)

xv6 文件系统在磁盘上有一个明确的布局。磁盘被划分为一系列固定大小（xv6中是512字节，但文件系统逻辑块 `BSIZE` 通常是1024字节或更大，一个逻辑块可能包含多个扇区）的**块 (blocks)**。从磁盘的起始位置开始，这些块的用途如下：

```
[ Boot Sector | Superblock | Log Blocks | Inode Blocks | Bitmap Blocks | Data Blocks ]
```

1.  **引导块 (Boot block - Block 0)**：
    *   磁盘的第一个块（通常是块0）。
    *   它包含引导加载程序（bootloader，源码在 `boot/bootasm.S` 和 `boot/bootmain.c`）。
    *   计算机启动时，BIOS 或固件会加载并执行这个块中的代码。引导加载程序的任务是将操作系统内核（存储在文件系统中的某个文件，或者直接在磁盘的后续扇区）加载到内存中并开始执行。xv6 的引导块本身不包含文件系统驱动，它只是简单地从磁盘的固定位置加载内核。

2.  **超级块 (Superblock - Block 1)**：
    *   紧随引导块之后（通常是块1）。
    *   它包含了关于整个文件系统的元数据，是文件系统得以识别和运作的关键。
    *   xv6 中由 `struct superblock` (定义在 `kernel/fs.h`) 描述：
        ```c
        // kernel/fs.h
        struct superblock {
          uint size;         // 文件系统总大小 (以块为单位)
          uint nblocks;      // 数据块的数量
          uint ninodes;      // inode 的数量
          uint nlog;         // 日志块的数量
          uint logstart;     // 第一个日志块的块号
          uint inodestart;   // 第一个 inode 块的块号
          uint bmapstart;    // 第一个位图块的块号
        };
        ```
    *   **`size`**: 文件系统映像的总块数。
    *   **`nblocks`**: 可用于存储文件内容和目录内容的数据块总数。
    *   **`ninodes`**: 文件系统中 inode 的总数。这也间接定义了文件系统可以拥有的最大文件（包括目录和设备文件）数量。
    *   **`nlog`**: 用于日志区域的块数。
    *   **`logstart`**: 日志区域在磁盘上的起始块号。
    *   **`inodestart`**: 第一个存储 inode 结构的块的块号。
    *   **`bmapstart`**: 第一个用于数据块分配的位图块的块号。
    *   当内核挂载文件系统时（在 `initlog()` 和 `readsb()` 中），它会读取这个超级块，以了解文件系统的布局和参数。

3.  **日志块 (Log Blocks)**：
    *   从 `sb.logstart` 开始，连续 `sb.nlog` 个块。
    *   用于实现崩溃恢复功能。文件系统操作对磁盘的修改（如分配一个块、写入 inode）会先以日志条目的形式写入这里。
    *   我们将在后续章节详细讨论日志机制。

4.  **Inode 块 (Inode Blocks)**：
    *   从 `sb.inodestart` 开始，占用一定数量的块，用于存储所有的 inode 结构。
    *   **Inode (索引节点)** 代表文件系统中的一个文件（包括普通文件、目录、设备文件）。它存储了文件的所有元数据，除了文件名（文件名存储在目录中）。
    *   xv6 中磁盘上的 inode 结构由 `struct dinode` (定义在 `kernel/fs.h`) 描述：
        ```c
        // kernel/fs.h
        // On-disk inode structure
        struct dinode {
          short type;           // 文件类型 (T_FILE, T_DIR, T_DEV)
          short major;          // 主要设备号 (仅当 type == T_DEV)
          short minor;          // 次要设备号 (仅当 type == T_DEV)
          short nlink;          // 硬链接数量 (有多少个目录项指向这个inode)
          uint size;            // 文件大小 (以字节为单位)
          uint addrs[NDIRECT+1]; // 数据块地址数组
                                // NDIRECT 个直接块地址
                                // 最后一个是间接块地址 (如果文件很大)
        };
        ```
    *   **`type`**: 文件类型，可以是：
        *   `T_FILE` (1): 普通文件。
        *   `T_DIR` (2): 目录文件。
        *   `T_DEV` (3): 特殊设备文件。
    *   **`major`, `minor`**: 如果文件类型是 `T_DEV`，这两个字段用于标识具体的设备驱动程序。
    *   **`nlink`**: 指向此 inode 的硬链接（即目录项）的数量。当 `nlink` 变为 0 时，表示没有文件名指向此 inode，文件内容和 inode 本身可以被回收。
    *   **`size`**: 文件内容的总大小（以字节为单位）。
    *   **`addrs[NDIRECT+1]`**: 一个包含数据块地址的数组。这是 inode 指向文件实际内容的关键。
        *   **`NDIRECT` (默认为12)**：前 `NDIRECT` 个条目是**直接块地址 (Direct block addresses)**。它们直接存储了文件的前 `NDIRECT` 个数据块在磁盘上的块号。
        *   **`addrs[NDIRECT]`**: 最后一个条目是**一级间接块地址 (Singly indirect block address)**。如果文件大于 `NDIRECT` 个块，这个地址会指向一个包含更多数据块地址的块（间接块）。一个间接块可以存储 `BSIZE / sizeof(uint)` 个块地址（例如，如果 `BSIZE` 是1024字节，一个地址是4字节，则一个间接块可以指向 256 个数据块）。
        *   xv6 不支持二级或三级间接块，所以文件大小有限制（大约 12*BSIZE + 256*BSIZE）。
    *   每个 inode 在磁盘上占用固定的大小（例如 64 字节）。一个 inode 块可以存储多个 `struct dinode`。可以通过 inode 号（`inum`）计算出它在哪个 inode 块以及块内的偏移。

5.  **位图块 (Bitmap Blocks)**：
    *   从 `sb.bmapstart` 开始，占用一个或多个块。
    *   用于跟踪哪些**数据块**是空闲的，哪些已被分配。
    *   磁盘上的每个数据块都对应于位图中的一个位。如果位是 0，表示对应的数据块空闲；如果是 1，表示已分配。
    *   当需要分配新的数据块时（例如，为文件写入新内容或创建新目录项），文件系统会扫描位图找到一个空闲位，将其设置为1，然后使用对应的块。释放块时则相反。
    *   xv6 没有为 inode 使用单独的位图；inode 的分配是通过查找 `type == 0` 的 `dinode` 来实现的。

6.  **数据块 (Data Blocks)**：
    *   这是文件系统中最大的区域，包含了所有文件和目录的实际内容。
    *   对于普通文件，数据块存储文件的字节流。
    *   对于目录，数据块存储一系列的目录项结构 (`struct dirent`)。

### 4. 文件和目录 (Files and Directories)

*   **普通文件 (Regular Files)**：
    *   由一个 `type == T_FILE` 的 inode 表示。
    *   其内容（字节序列）存储在 inode 的 `addrs` 数组指向的数据块中。
    *   `size` 字段记录了文件的确切字节大小。

*   **目录 (Directories)**：
    *   由一个 `type == T_DIR` 的 inode 表示。
    *   目录的内容也是存储在数据块中，但这些数据块的组织方式是特殊的：它们包含一个**目录项 (Directory Entries)** 的列表。
    *   每个目录项由 `struct dirent` (定义在 `kernel/fs.h`) 描述：
        ```c
        // kernel/fs.h
        struct dirent {
          ushort inum;    // 该目录项对应的 inode 号
          char name[DIRSIZ]; // 文件名 (DIRSIZ 通常是14)
        };
        ```
    *   **`inum`**: 这个目录项所指向的文件的 inode 号。
    *   **`name`**: 文件名字符串（以空字符结尾，最大长度为 `DIRSIZ-1`）。
    *   例如，如果目录 `/usr` 包含一个文件 `xv6`，那么 `/usr` 目录对应的数据块中会有一个 `dirent` 结构，其 `name` 字段是 "xv6"，`inum` 字段是 `xv6` 文件的 inode 号。
    *   每个目录至少包含两个特殊的目录项：
        *   `.` (点)：指向目录自身的 inode。
        *   `..` (点点)：指向其父目录的 inode。

*   **根目录 (Root Directory)**：
    *   文件系统的最顶层目录，用路径 `/` 表示。
    *   它本身也是一个目录，有自己的 inode。xv6 规定根目录的 inode 号是 `ROOTINO` (通常为1)。
    *   内核在启动时会读取根 inode (`iget(ROOTDEV, ROOTINO)`)。

### 5. 路径名 (Pathnames)

用户和程序通过路径名来定位文件系统中的文件或目录。
*   **绝对路径 (Absolute Paths)**：从根目录 `/` 开始的路径，例如 `/usr/bin/ls`。
*   **相对路径 (Relative Paths)**：不以 `/` 开始的路径，它是相对于进程的当前工作目录 (current working directory, `cwd`) 来解析的。例如，如果当前目录是 `/usr`，那么路径 `bin/ls` 就等同于 `/usr/bin/ls`。
*   **路径名解析 (Name Resolution)**：将一个路径名转换为对应的 inode 的过程。这通常涉及从一个起始 inode（根目录 inode 或当前目录 inode）开始，逐级读取目录内容，查找路径中的下一个组件名，获取其 inode 号，再读取该 inode，直到路径的所有组件都被处理完毕。函数 `namei` 和 `nameiparent` 在 xv6 中执行此功能。

### 6. 设备文件 (Device Files)

在 Unix 和 xv6 中，设备（如控制台）也被抽象为文件系统中的文件。
*   由一个 `type == T_DEV` 的 inode 表示。
*   这种 inode 不指向数据块。相反，它的 `major` 和 `minor` 设备号用于标识特定的设备驱动程序。
*   当用户程序对设备文件执行 `read` 或 `write` 系统调用时，文件系统层会将这些操作转发给由 `major` 号确定的设备驱动程序中的相应读/写例程。
*   例如，xv6 中的控制台设备（`user/console.c` 中可见）被实现为一个设备文件，其 `major` 号为 `CONSOLE_MAJOR` (通常为1)。读写控制台文件实际上就是与控制台驱动交互。

这一概览为我们理解 xv6 文件系统的内部工作机制打下了基础。后续章节将更详细地探讨 inode 管理、路径名解析、文件读写、日志系统等具体方面。
